# Fork patch manifest

The `gabe/fork` branch is a downstream patch stack on `main` at upstream
commit `d6a7ca66` (soju06/codex-lb). This file is the human review surface
for what the fork carries beyond upstream and why.

## Maintained logical patches

| Patch | SHA | Category | Upstream status |
|---|---|---|---|
| `native-giveup-retryable-error` | `862d5cb3` | defensive | Not yet upstreamed. When codex-lb exhausts its own retries/replays for an upstream capacity/overload error on behalf of a native Codex client, it used to re-raise after the 200 had already been sent, closing the SSE/WS stream with zero bytes ("Stream disconnected before completion"). This patch emits a terminal `response.failed` with `error.code = "rate_limit_exceeded"` and a "try again in `<N>`s" message instead, so codex-rs's own reconnect logic (which treats `server_is_overloaded`/`slow_down` as terminal and only retries + parses a delay from `rate_limit_exceeded`) engages instead of the client retrying blind. Touches `app/core/errors.py`, `app/modules/proxy/api.py` (both native give-up gates in `_stream_response_error_events` / `_normalize_public_responses_stream`), `app/modules/proxy/_service/http_bridge/request_submit.py` (preserves the upstream cause on the denied-anchor fail-closed raise), and `app/modules/proxy/_service/websocket/helpers.py` (`_sanitize_websocket_terminal_error_fields` relabels `server_is_overloaded`/`slow_down` terminal frames the same way). Non-native/OpenAI-compatible clients are unaffected. Spec updated: `openspec/specs/responses-api-compat/spec.md` ("Native Codex preserves upstream failure lifecycle"). Side effect: denied-anchor failures in `http_bridge/request_submit.py` now record `upstream_error_code=previous_response_not_found` (previously `stream_incomplete`) in RequestLog telemetry. |
| `self-heal-denied-continuity-anchors` | `TBD` | defensive | Not yet upstreamed. After an LB restart, a denied proxy-injected `previous_response_id` anchor made every retry on that session hit the same `denied_proxy_anchor_before_dispatch` fail-closed raise forever: native Codex clients always resend full input and never set the anchor themselves, so they had no way to drop it and looped their reconnect budget to zero (observed live as 15+ minutes of `Reconnecting... n/5` before a manual restart cleared it). This patch changes the dispatch-site check in `app/modules/proxy/_service/http_bridge/request_submit.py` (`_submit_http_bridge_request_with_handoff`, the `denied_proxy_anchor_before_dispatch` block) to self-heal in place at most once per client request: when the request's pre-injection body is known to have carried full context on its own (`request_state.proxy_injected_anchor_had_full_resend_payload` and `request_state.fresh_upstream_request_text`), it drops the anchor and reissues the same submission with that captured full-context text instead of raising, recording `_record_continuity_self_heal` (new sibling to `_record_continuity_fail_closed`, `app/modules/proxy/_service/observability.py` + `codex_lb_continuity_self_heal_total` in `app/core/metrics/prometheus.py`) instead. A second denial in the same submission still fails closed via the existing raise (bounded by the new `_WebSocketRequestState.continuity_self_healed` flag in `app/modules/proxy/_service/support.py`). When no full-context body is available (a reattach/replay stage that only carries the anchor), the raise is kept, but the denied id is now also dropped from `session.denied_proxy_injected_anchor_ids` so the client's own next retry is not re-anchored to the same dead response id. Also fixes a stale comment in `app/modules/proxy/api.py` (~8420s) that claimed Codex's reconnect logic only retries `rate_limit_exceeded`; it retries any non-terminal code, `rate_limit_exceeded` is only special for the parsed retry delay. Spec updated: `openspec/specs/responses-api-compat/spec.md` ("Explicit upstream previous-response denials retire proxy-injected anchors"). Extended to the "owner account unavailable" admission-time failure too: `app/modules/proxy/_service/http_bridge/streaming.py`'s `owner_unavailable_allows_account_neutral_replay`/`switch_to_account_neutral_replay` session-creation retry (previously only reachable via durable-lookup reconstruction) now also self-heals on the same proxy-injected-full-resend discriminator when a `previous_response_owner_unavailable` raise hits a cooldown/overloaded owner, recording `_record_continuity_self_heal(reason="owner_unavailable")`; without full context the raise is unchanged (no persistent per-request pin exists there to retire, since the owner is re-resolved fresh from durable state on each client retry). The proxy-injected-full-resend gate was factored out of `streaming.py`'s closure into a shared, request-state-only predicate `owner_unavailable_allows_proxy_injected_self_heal` (`app/modules/proxy/_service/support.py`), and the WebSocket connect path now uses it too: `_select_websocket_connect_account` (`app/modules/proxy/_service/websocket/mixin.py`) applies the same self-heal, combined with the WS-side `_websocket_request_text_is_account_neutral_fresh_replay` account-neutral check, before both of its `previous_response_owner_unavailable` raises (preferred-account mismatch and preferred-account-missing), dropping the anchor/owner pin and re-running `_select_account_with_budget_compatible(..., require_preferred_account=False)`; a second failure there still falls through to the original fail-closed raise unchanged. Known remaining fail-closed sites not covered by any self-heal (left as-is, listed for future work): `app/modules/proxy/_service/http_bridge/mixin.py`, `app/modules/proxy/_service/streaming/retry.py`, `app/modules/proxy/_service/compact.py`, `app/modules/proxy/_service/sticky_selection.py`. |
