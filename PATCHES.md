| `native-giveup-retryable-error` | `862d5cb3` | defensive | Not yet upstreamed. When codex-lb exhausts its own retries/replays for an upstream capacity/overload error on behalf of a native Codex client, it used to re-raise after the 200 had already been sent, closing the SSE/WS stream with zero bytes ("Stream disconnected before completion"). This patch emits a terminal `response.failed` with `error.code = "rate_limit_exceeded"` and a "try again in `<N>`s" message instead, so codex-rs's own reconnect logic (which treats `server_is_overloaded`/`slow_down` as terminal and only retries + parses a delay from `rate_limit_exceeded`) engages instead of the client retrying blind. Touches `app/core/errors.py`, `app/modules/proxy/api.py` (both native give-up gates in `_stream_response_error_events` / `_normalize_public_responses_stream`), `app/modules/proxy/_service/http_bridge/request_submit.py` (preserves the upstream cause on the denied-anchor fail-closed raise), and `app/modules/proxy/_service/websocket/helpers.py` (`_sanitize_websocket_terminal_error_fields` relabels `server_is_overloaded`/`slow_down` terminal frames the same way). Non-native/OpenAI-compatible clients are unaffected. Spec updated: `openspec/specs/responses-api-compat/spec.md` ("Native Codex preserves upstream failure lifecycle"). Side effect: denied-anchor failures in `http_bridge/request_submit.py` now record `upstream_error_code=previous_response_not_found` (previously `stream_incomplete`) in RequestLog telemetry. |
| `self-heal-denied-continuity-anchors` | `TBD` | defensive | Not yet upstreamed. After an LB restart, a denied proxy-injected `previous_response_id` anchor made every retry on that session hit the same `denied_proxy_anchor_before_dispatch` fail-closed raise forever: native Codex clients always resend full input and never set the anchor themselves, so they had no way to drop it and looped their reconnect budget to zero (observed live as 15+ minutes of `Reconnecting... n/5` before a manual restart cleared it). This patch changes the dispatch-site check in `app/modules/proxy/_service/http_bridge/request_submit.py` (`_submit_http_bridge_request_with_handoff`, the `denied_proxy_anchor_before_dispatch` block) to self-heal in place at most once per client request: when the request's pre-injection body is known to have carried full context on its own (`request_state.proxy_injected_anchor_had_full_resend_payload` and `request_state.fresh_upstream_request_text`), it drops the anchor and reissues the same submission with that captured full-context text instead of raising, recording `_record_continuity_self_heal` (new sibling to `_record_continuity_fail_closed`, `app/modules/proxy/_service/observability.py` + `codex_lb_continuity_self_heal_total` in `app/core/metrics/prometheus.py`) instead. A second denial in the same submission still fails closed via the existing raise (bounded by the new `_WebSocketRequestState.continuity_self_healed` flag in `app/modules/proxy/_service/support.py`). When no full-context body is available (a reattach/replay stage that only carries the anchor), the raise is kept, but the denied id is now also dropped from `session.denied_proxy_injected_anchor_ids` so the client's own next retry is not re-anchored to the same dead response id. Also fixes a stale comment in `app/modules/proxy/api.py` (~8420s) that claimed Codex's reconnect logic only retries `rate_limit_exceeded`; it retries any non-terminal code, `rate_limit_exceeded` is only special for the parsed retry delay. Spec updated: `openspec/specs/responses-api-compat/spec.md` ("Explicit upstream previous-response denials retire proxy-injected anchors"). Extended to the "owner account unavailable" admission-time failure too: `app/modules/proxy/_service/http_bridge/streaming.py`'s `owner_unavailable_allows_account_neutral_replay`/`switch_to_account_neutral_replay` session-creation retry (previously only reachable via durable-lookup reconstruction) now also self-heals on the same proxy-injected-full-resend discriminator when a `previous_response_owner_unavailable` raise hits a cooldown/overloaded owner, recording `_record_continuity_self_heal(reason="owner_unavailable")`; without full context the raise is unchanged (no persistent per-request pin exists there to retire, since the owner is re-resolved fresh from durable state on each client retry). The proxy-injected-full-resend gate was factored out of `streaming.py`'s closure into a shared, request-state-only predicate `owner_unavailable_allows_proxy_injected_self_heal` (`app/modules/proxy/_service/support.py`), and the WebSocket connect path now uses it too: `_select_websocket_connect_account` (`app/modules/proxy/_service/websocket/mixin.py`) applies the same self-heal, combined with the WS-side `_websocket_request_text_is_account_neutral_fresh_replay` account-neutral check, before both of its `previous_response_owner_unavailable` raises (preferred-account mismatch and preferred-account-missing), dropping the anchor/owner pin and re-running `_select_account_with_budget_compatible(..., require_preferred_account=False)`; a second failure there still falls through to the original fail-closed raise unchanged. 2026-09-14 live incident (request `8b93e680-cea6-4c7f-bce4-54f7a72fd107`, account `0f36313f-...` marked unavailable after 24x `server_is_overloaded`, native Codex client, full input always sent, `store:false`): the admission-time `http_bridge_routing stage=admission reason=smart_turn_state` log was immediately followed by the `previous_response_owner_unavailable` 502 with zero `continuity_self_heal` lines. Root-caused to a third, previously-uncovered continuity shape: `_stream_via_http_bridge`'s `fresh_reattach_can_use_durable_anchor` block (`app/modules/proxy/_service/http_bridge/streaming.py`, the `client_unanchored_full_resend` branch, ~line 1736) skips injecting any `previous_response_id` anchor at all when the client's own full-resend payload already proves (`_VerifiedDurableFullResend.matches`) it carries the durable turn's complete context — but `request_state.preferred_account_id` is still pinned to the durable owner via hard session/turn-state affinity (`bridge_session_key.strength == "hard"`). Because no anchor was ever injected, `request_state.proxy_injected_previous_response_id` stays `False`, so the existing `owner_unavailable_allows_proxy_injected_self_heal` predicate denied self-heal and the request failed closed even though the client's own body was already a valid account-neutral replay body. Call chain: `app/modules/proxy/_service/streaming/retry.py:227` (`record_http_bridge_routing(stage="admission", ...)`) → `app/modules/proxy/api.py:7005` (`stream_http_responses`) → `streaming.py:2237` (`_get_or_create_http_bridge_session`) → `mixin.py:1661` (`_create_http_bridge_session`) → `mixin.py:1729` (`_select_account_with_budget_for_stream`) → `app/modules/proxy/_load_balancer/sticky_selection.py:774` (`hard_affinity_saturated`) → `mixin.py:1757` (raises `previous_response_owner_unavailable`) → caught at `streaming.py:2283`, denied by `owner_unavailable_allows_account_neutral_replay` → re-raised. | `file-owner-bound-usage-limit-surface` | `7b7ba536` | defensive | Not yet upstreamed. Investigated whether a usage-limit 429 on a file-owner-bound image request (`_stream_owner_bound_to()`'s `account.id == file_preferred_account_id` branch, `app/modules/proxy/_service/streaming/retry.py`) could safely fail over like the existing `verified_fresh_replay_payload` escape a few lines above it does for turn-state owners. It cannot: `file_preferred_account_id` is only ever set when `extract_input_file_ids()` (`app/core/openai/requests.py`) finds a durable `file_id`/`sediment://` reference in the request's `input_image`/`input_file` items (a genuinely inline `data:`/plain-URL image never sets it, so it was never owner-bound by this branch in the first place) — and `_verified_cross_transport_fresh_replay()` (`retry.py`) unconditionally returns `None` whenever `extract_input_file_ids()` is non-empty. So whenever this branch is the reason a stream is owner-bound, `verified_fresh_replay_payload` is guaranteed `None`: replaying the request on another account would hand that account a file handle it does not own. No unbind is implemented. Instead, `_stream_with_retry`'s primary (non-post-refresh) surface path now folds an absolute reset deadline into the surfaced 429's `message` (`_stamp_file_owner_bound_rate_limit_surface`, `retry.py`) and logs the decision (`account_id`, `file_preferred_account_id`, `reset_at`) so a file-owner-bound usage-limit rejection is diagnosable and actionable instead of a bare 429. Test: `test_file_owner_bound_usage_limit_429_surfaces_with_reset_time_and_logs` (`tests/unit/test_streaming_retry_virtual_time.py`), red on the pre-patch code (asserted via `git stash`), green after. The symmetric post-refresh surface path (`retry.py` ~3290) and the compact/websocket transports were left unpatched — same live-evidence request (`1f177bde-2be7-4eef-ae3c-4d63022fb778`) only exercised the primary plain-stream path. |
